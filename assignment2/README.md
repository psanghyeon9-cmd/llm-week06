# 과제 2 — Mock 분류기 확장

수업의 `mock_llm.py`와 `Week62.py`를 바탕으로 불량 응답 주입과 실패 집계를 구현했습니다. 실제 API나 외부 네트워크를 사용하지 않으며 Python 표준 라이브러리만으로 실행됩니다. 수업 원본은 `source/`, 제공된 리뷰 200건은 `data/reviews_sample.csv`에 보존했습니다.

## 실행

VS Code에서 `llm-week6` 폴더를 열고 PowerShell 터미널에서 실행합니다.

```powershell
py -X utf8 assignment2/run_pipeline.py --seed 42 --output-dir assignment2/evidence
```

`--seed 42`는 확인 가능한 재현용 난수 설정입니다. 시행 결과를 고르기 위해 seed를 탐색하지 않았습니다. seed를 생략하면 매번 다른 결과가 나올 수 있습니다. 입력 파일 경로는 기본적으로 스크립트 위치를 기준으로 찾습니다. 별도의 CSV는 `--input 경로`로 지정하며 `review_text` 열이 필요합니다.

## 구현

1. `mock_llm.py`: 매 호출에서 `random() < 0.20`이면 코드펜스·사족·잘린 JSON 중 하나를 `choice()`로 선택합니다. 정상 응답 내용과 키워드 우선순위는 수업 원본을 유지했습니다.
2. `classify.py`: 완전히 닫힌 코드펜스만 제거하고 JSON 파싱 및 스키마를 검증합니다. 사족과 잘린 JSON은 복구하지 않고 `None`을 반환합니다. category·sentiment 허용값과 score의 정수 여부 및 1~5 범위도 검사하며 bool은 점수로 허용하지 않습니다.
3. `run_pipeline.py`: 실패를 세고 다음 행을 계속 처리합니다. 처리 건수는 성공과 실패를 포함한 입력 행 수이며, 분류별 합계에는 성공한 리뷰만 포함합니다. 마지막에 `처리 N건 / 실패 M건`을 출력합니다.

`mock_response_kind`는 주입 유형을 집계하기 위한 모의 실험용 표시입니다. 파서는 이 표시를 신뢰해 성공 여부를 결정하지 않고 실제 응답 문자열을 검사합니다. 복구 건수도 실제 코드펜스와 파싱 성공을 확인해 셉니다. 실제 API는 이 표시를 제공한다고 가정할 수 없습니다.

수업의 프롬프트에는 환불이 빠져 있지만 원본 Mock과 검증 목록에는 포함되어 있으므로, 과제 2에서는 `배송/품질/가격/환불/서비스/기타`로 일치시켰습니다. 과제 1의 문의 유형·긴급도 스키마와 과제 2의 리뷰 category·sentiment·score 스키마는 서로 다릅니다.

## 실제 실행 결과

| 항목 | 건수 |
|---|---:|
| 전체 처리 | 200 |
| 정상 응답 | 158 |
| 불량 응답 | 42 |
| 코드펜스 | 17 |
| 사족 | 15 |
| 잘린 JSON | 10 |
| 코드펜스 복구 | 17 |
| 성공 | 175 |
| 실패 | 25 |

최종 출력은 **처리 200건 / 실패 25건**입니다. 불량 42건 중 코드펜스 17건은 제거 후 정상 JSON으로 처리되어 실패에서 제외됩니다. 따라서 실패는 사족 15건 + 잘린 JSON 10건 = 25건이며, 158 + 17 = 175건이 성공했습니다. 실제 불량 발생률은 42/200 = 21%로, 각 호출의 주입 확률 20%와 정확히 같을 필요는 없습니다.

성공 분류는 기타 113건, 배송 41건, 품질 16건, 환불 5건으로 합계 175건입니다. 실행 로그는 [run_seed42.txt](evidence/run_seed42.txt), 집계값은 [summary.json](evidence/summary.json), 행별 성공·실패는 [row_results.csv](evidence/row_results.csv)에 있습니다. 행 번호는 헤더를 제외한 데이터 행의 1부터 시작합니다.

## 검증

```powershell
py -X utf8 -m unittest discover -s assignment2 -p test_pipeline.py -v
```

실제 실행에서 9개 테스트가 통과했습니다. 20% 경계값, 원본 정상 결과 유지, 세 불량 유형의 처리, 파싱과 스키마 거부, 모의 표시와 무관한 검증, 실패 이후 행 처리 지속, 잘못된 입력, CSV 열 확인, 200건의 재현성과 집계 불변식을 검증했습니다. 실패 뒤 마지막 정상 행까지 처리되는 별도 테스트가 있어 단순히 오류 없이 종료됐는지만 검사하지 않습니다. 테스트 출력은 [tests.txt](evidence/tests.txt)에 있습니다.

## 해석의 한계와 보안

Mock은 키워드에 따라 고정 응답을 반환하므로 부정적인 배송 리뷰에도 긍정을 반환할 수 있습니다. 이 과제는 리뷰 분류 정확도가 아니라 응답 형식 오류에 대한 파이프라인의 처리 능력을 검증합니다. `usage`의 토큰 수 역시 수업 원본의 고정 모의 값으로, 실제 비용이나 토큰 사용량이 아닙니다.

실제 고객 정보나 API 키를 추가하지 않았고, 제공된 실습 리뷰만 사용했습니다. 리뷰 문자열은 실행하지 않으며 사용자 입력과 모델 출력은 각각 검사합니다. 행별 증빙에는 리뷰 본문을 복사하지 않고 원본 데이터 행 번호와 결과만 남깁니다. 선택 과제인 사족 복구는 구현하지 않았습니다. 키·문자열 내용이 임의로 잘린 JSON을 억지로 보완하여 성공으로 처리하지 않습니다.
